# AgentZuno development instructions

## Stack and structure

- Use Solid.js with JavaScript/JSX and Vite. Use Solid components and reactive primitives; do not substitute React or plain DOM rendering.
- Keep route-level screens in `src/pages/`, shared page shells in `src/layouts/`, reusable UI in `src/components/`, shared state in `src/context/`, and API calls in `src/services/`.
- Keep the Express API in the independent `api/` project. It must run on its own locally and with `docker compose up --build api`. The web app and API must remain separate Docker services.
- Keep mock JSON in `api/mock-data/`. Serve it through Express; never import mock records directly into frontend components. MongoDB via the official Node.js driver is authorized for all created records and uploaded files/images. Keep the initial examples as JSON mocks; do not add live integrations until requested.
- Require authentication for every workspace page and application data endpoint. Keep only the landing page, login/registration, and identity callbacks public. Demo logins and sessions are disabled. Select authorized records on the API server; never expose all users’ records and filter them in the browser.
- Keep included demo accounts clearly labeled and fixture credentials fictional. Registered accounts and workspace IDs persist in MongoDB; hash passwords with scrypt and persist only hashed session tokens. Require authentication for creation/upload/save actions and enforce workspace ownership on the API.

## Simple, readable code

- Prefer straightforward control flow, clear names, and small functions with one purpose. Keep code concise and self-documenting.
- Use the simplest solution that serves the current feature. Avoid speculative abstractions, generic frameworks, clever shortcuts, and unnecessary dependencies.
- Keep JSX readable. Extract a component when it clarifies a distinct UI responsibility; do not split trivial markup into many tiny files.
- Add comments only to explain a non-obvious decision or constraint. Keep documentation and user-facing updates concise.

## Naming conventions

- Use `PascalCase` for Solid components and their JSX files, such as `ArticleCard.jsx`.
- Give route screens a `Page` suffix and shared shells a `Layout` suffix, such as `HelpPage.jsx` and `WorkspaceLayout.jsx`.
- Use `camelCase` for variables, functions, API modules, and service files. Use descriptive verbs for actions, such as `loadWorkspace` and `signOut`.
- Name boolean values with `is`, `has`, or `can` where helpful, such as `isGuest` or `canEdit`. Use plural names for arrays, such as `articles`.
- Use `kebab-case` for CSS classes, URL segments, and JSON fixture filenames. Use `camelCase` for JSON properties.
- Avoid unexplained abbreviations and generic names such as `data1`, `tmp`, or `handleStuff`.

## Design and verification

- Use the exact brand casing **AgentZuno**, locally hosted Inter for application and authentication screens, and Shippori Mincho for the public landing page. Preserve the black homepage, neural background, and reduced-motion support.
- Default the workspace to dark mode using the landing page’s black and cool blue palette. Keep a light-mode toggle and preserve the device preference. Use shared theme variables so all pages remain consistent.
- The workspace root is Inbox for Admins and Agents, showing access-filtered support tickets in the shared RecordTable. Users land on Chat and see only Chat, Tickets, and Knowledge in navigation. Knowledge visibility never grants source access. Never claim to generate AI responses without a configured provider.
- Keep the workspace sidebar a 45px icon rail with right-side hover and keyboard-focus tooltips, a primary create button above Search, a small separator, and a bottom account popup.
- Keep all modal backdrops and other overlays within the main content area, excluding the sidebar. Center dialogs within that area and use the shared sidebar-width variable.
- The workspace is also the public product tour and help center. Keep examples and unfinished capabilities clearly labeled.
- Update the README when setup or behavior changes. Keep both Docker and local Node development working.
- After every change, rebuild and restart the affected Docker services before finishing. Use `docker compose up --build -d --force-recreate <services>` so the running containers include the latest changes, and verify the affected services are running and healthy where health checks exist.
- Keep all code formatted and easy to read in VS Code. Honor `.editorconfig` and `.vscode/settings.json`: two-space indentation, LF line endings, final newlines, and Prettier format-on-save. Recommend the Prettier VS Code extension through `.vscode/extensions.json`.
- Format all code consistently with Prettier. Run `npm run format` after edits and `npm run format:check` before finishing.
- Run relevant tests, especially for authentication and isolation between guest and personal data. Add tests for behavior, not incidental implementation details.

- Article forms use Title and Body, with free Tiptap core/extensions in a Solid component. Persist sanitized article HTML and image binaries through the Express API and official MongoDB driver. Require an authenticated owner for writes and file/image reads; never accept an owner ID from the client.

- Search overlays have one scrollable results region and lock background page scrolling. Keep the sidebar interactive; sidebar actions dismiss the current overlay before opening another action.

- Use simple route titles for page headings. Do not add promotional eyebrows, introductions, or preview banners above page content. Login uses `/login`; registration uses the dedicated `/register` page titled Register with password guidance only on validation failure; new accounts receive a persistent workspace ID used in `/workspace/:workspaceId/...` routes.

- Live integrations are now authorized. Keep adapter support truthful: Zendesk and Confluence have delegated source checks; Notion imports require explicit AgentZuno-managed permissions. Unsupported adapters must fail closed; normalized export imports are explicitly managed snapshots.
- Never silently fall back from source permissions to AgentZuno permissions. Managed copies require explicit owner acceptance and remain owner-only until organization membership/group authorization is implemented.
- Before returning imported titles, snippets, citations, or text, intersect workspace ownership, current agent grants, token identity, and source or managed access policy. Source errors and unknown permissions deny access.
- Encrypt source credentials and OIDC client secrets on the server. Never include credentials in frontend workspace data, logs, external model context, query results.
- OIDC identity-provider settings are owner-only. Use issuer/subject identity binding, PKCE/state/nonce, validated ID tokens, and safe public HTTPS endpoints. Identity login never automatically grants source knowledge access. Public demo accounts cannot configure identity providers or live source credentials.
- Keep ingestion snapshots generation-scoped, publish only completed syncs, and retain the last complete snapshot after a failed sync. Document provider limits and unimplemented adapters, token refresh, webhooks, SCIM/groups honestly.

## Shared controls and connection security

- Use `src/components/Dropdown.jsx` for every select/dropdown field. Keep one shared custom style, accessible labels, keyboard navigation, outside-click dismissal, and hidden form values. Do not add native HTML selects. Single-option permission modes default automatically and remain read-only.
- Do not restore the managed-copy authorization checkbox. Submitting the explicitly labeled managed connection/import action records the owner’s selection; never silently change a source-enforced connection into a managed one.
- Offer only authentication methods implemented by the selected adapter. Prefer OAuth. API-key/basic-token methods remain managed owner-only copies; do not present shared credentials as delegated end-user permission verification. Do not collect deprecated Zendesk account passwords.
- Keep OAuth client secrets server-side. Bind short-lived, single-use authorization state to both the authenticated owner/workspace and an HttpOnly browser cookie. Use fixed provider endpoints and fixed callback URLs, deny redirects during token exchanges, and never expose provider tokens in browser URLs or logs. Do not claim PKCE, token refresh, or provider support unless implemented and tested.
- Validate all untrusted API input server-side, including authentication method, credential bounds, tenant/cloud identifiers, knowledge-base ownership, and permission mode. Fail closed on malformed inputs, expired/replayed OAuth state, unknown access, and provider failures. Frontend validation supplements server enforcement.
- Before finishing security-sensitive changes, run behavioral authorization/isolation and credential/OAuth tests, the production build, and Prettier checks. Document remaining limits honestly; passing tests does not certify that all code is secure.

## Background jobs and AI chat

- Put only IDs and scheduling metadata in queue payloads. Load encrypted credentials inside the worker. Deduplicate scheduled imports, use MongoDB leases, bound concurrency, and respect provider retry delays with exponential backoff and jitter. Recover queued work from MongoDB after outages; never claim exactly-once execution across Redis/MongoDB.
- Chat requires a registered account. Scope every chat, message, provider setting, and worker write to the owner/workspace. Preserve guest drafts in short-lived tab session storage across login/registration, without putting prompt text in URLs. Never auto-submit a draft without the visitor’s original explicit submission.
- Keep AI provider endpoints and model IDs allowlisted. Encrypt API keys, return only key-presence metadata, validate instructions and generation limits, and render model responses through the shared sanitized Markdown renderer; user messages remain escaped text. Instructions cannot override server authorization. Do not automatically send workspace knowledge to AI providers; retrieval must pass the existing source/agent policies first.
- All workspace page titles share the Dashboard greeting size. Chat lives below Home in the icon rail; its composer belongs on Chat, not Dashboard. Keep status indicators accessible and honor reduced motion.

- Keep apps and saved connections on Connections alphabetically sorted by display name (A–Z, case-insensitive, numeric-aware), including filtered/search results. Sort category choices alphabetically too.

- Use the book-and-pen icon for Knowledge navigation and summaries. Uppercase the account initial in the profile circle. Recent Activity shows a distinct colored icon badge for each content type and a text-labeled status with a colored dot under Content. Use actual record state where available; never label a saved article as Published without a publication state. Ensure statuses remain understandable without color and work in both themes.

- Imports support an existing knowledge base or source-named knowledge bases. Validate destination ownership, map by stable source ID within the owning connection/workspace, and preserve names. Missing source group metadata fails the import instead of silently bundling content. New bases require explicit agent grants and must never inherit broader agent/token access automatically.

- Keep shared dropdowns closed after mouse or keyboard selection. Prevent option clicks inside labels from reactivating the trigger.
